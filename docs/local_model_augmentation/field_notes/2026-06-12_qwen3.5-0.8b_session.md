# Field notes — qwen3.5:0.8b, rlm mode, session `0f9cd627`

First real-world small-model session after the resource-fix campaign
(commits `9c6b8dd`..`04509fd`). The machine stayed responsive (RC1-RC3
fixes held). The *behavioral* failures below are the evidence base for
the plan-01 amendment, plan 03 Signal C, and plan 04.

**Setup**: `--harness-mode=rlm`, qwen3.5:0.8b via Ollama, cwd = the
anie repo. User prompt: *"Good morning! Can you tell me the time?"*

**Outcome**: 23 assistant turns, 22 tool calls, 8 errored (36%). The
question was never answered well.

## F1 — Hallucinated tool name `tool_calls` (6 calls, 100% failure, no recovery)

The model invented a tool named `tool_calls` — almost certainly the
OpenAI wire-format key (`"tool_calls": [...]`) leaking into its idea of
the tool catalog. Its arguments reveal real intent: some are
bash-shaped (`{"command": ..., "timeout": "5"}`), some recurse-shaped
(`{"query": "summary id=None kind=message_grep pattern=..."}`).

Today "Tool not found" goes straight to a synthetic failure: the
repair round (plan 01 PR2) only fires on schema-validation failures of
*known* tools, so all six calls burned a full turn each. A
deterministic name-rescue (validate the args against registered
schemas; remap when exactly one matches) would have recovered the
bash-shaped ones without any model round-trip.

## F2 — rlm ledger syntax leaks into tool arguments

The ledger format (`<value> (id=<call_id>)`, `scope.kind=message_grep`,
`pattern=<regex>`) appears *inside* bash commands and the fake tool's
args, e.g.:

```
cat <(ls) (id=ollama_tool_call_0_1 2>/dev/null || echo "...")
grep "OLLAMA_TOOL_CALL_9" ...   # treats call ids as file content
```

The current ledger + rlm augment is a ~700-token instruction manual
(`RLM_SYSTEM_PROMPT_AUGMENT`, controller.rs:2778) that teaches syntax a
0.8B model cannot hold — it becomes attractive-nuisance text the model
pattern-matches into commands. The recurse scope shapes
(`scope.kind`/`tool_call_id`/`pattern`) are beyond this tier.

## F3 — `additionalProperties: false` violations, then repair made it worse

`bash` was called with hallucinated extra args
(`{"command": "find ...", "limit": "15", "path": "..."}`); bash's
schema is `additionalProperties: false` (bash.rs:104), so validation
failed. Coercion (PR1) has no rule for unknown properties, so the
generative repair round fired — and the 0.8B model "fixed" the call by
quoting the whole command as an argument to bash:
`{"command": "bash \"find . -name ...\""}` → exit 127. Two repair
rounds, two broken rewrites (`argument_repair_rounds: 2` on a failed
result). Deterministically **stripping unknown properties** would have
rescued the original call perfectly — the `command` was fine.

## F4 — Semantic search loop (10 web_search calls, all "successful")

Ten escalating near-duplicate queries for "what time is it", each
hallucinating more specifics (invented dates 2026-06-13, "May 9",
"5pm EST", "hexbin timestamp"). The failure-loop detector requires
*identical* `(tool, args_hash)` and the calls all "succeeded", so
nothing fired. The ledger is supposed to prevent re-searching but the
model can't parse it (F2). This is the small-model loop signature:
*similar-but-not-identical* calls that never error.

## F5 — Prompt weight: 11,291 tokens at turn 0 against a 16,384 ceiling

Input tokens per assistant turn: 11291 → 20181 over the session. The
system prompt + catalogs consume ~69% of the rlm active-context ceiling
before the conversation starts. Contributors (this cwd):

- 10 skills discovered (bundled 4 + project `.claude/skills/` 2 + user
  `~/.claude/skills/` — including a 32KB `skill-creator` body that
  triggers the soft-cap warning at every launch, and `analyze-adl`
  which fails parsing at every launch).
- The anie repo's own `CLAUDE.md` (~8KB) + user CLAUDE.md as context
  files.
- Full tool catalog with long descriptions + PR3 example block.
- The ~700-token rlm augment (F2).

A 0.8B model with an effective ~5k tokens of working room cannot also
hold a conversation. Eviction can't help: the prompt is not evictable.

## F6 — Bash overcomplication (model-side, harness-relevant)

Every bash attempt was a compound one-liner (`||` fallbacks, heredocs,
process substitution, `sleep infinity`) — e.g. three failed attempts to
get the date where plain `date` would have worked. Harness can't fix
the model, but guidance text and the PR3 example shape can stop
*encouraging* complexity ("one simple command per call; no fallback
chains — the harness reports errors back to you").

## What worked

- No resource contention; machine responsive throughout (RC1-RC3 ✓).
- Repair rounds fired (2×) and produced schema-valid output (the
  output was semantically wrong — see F3 — but the machinery worked).
- Failure wrapping (re-verify directives) present on all 8 errors.
- The session log shape (errors, details markers) made this analysis
  trivial — the observability investment is paying off.
